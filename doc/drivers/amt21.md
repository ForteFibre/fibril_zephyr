# AMT21x アブソリュートエンコーダ（`cui,amt21`）

Same Sky（旧 CUI Devices）の AMT21 シリーズを、半二重 RS485 バス上で読むドライバ。
12 bit と 14 bit の両解像度、単回転版と多回転版、2 Mbps 版と可変データレート版のいずれにも対応する。

共通のエンコーダインタフェースは [include/drivers/encoder.h](../../include/drivers/encoder.h)、このドライバ固有の診断は [include/drivers/encoder/amt21.h](../../include/drivers/encoder/amt21.h) にある。

## デバイスの構成

1 つのバスノードが UART を占有し、配下のエンコーダ子ノードを順番にポーリングする。
エンコーダはそれぞれ独立した device として現れる。

読み出しはキャッシュ済みのスナップショットから返し、バスの完了を待たない。
制御ループから呼んでもブロックしない。

実機で通ったデバイスツリーの記述は [samples/drivers/amt21/boards/fibril_robomaster_miniv1.overlay](../../samples/drivers/amt21/boards/fibril_robomaster_miniv1.overlay) にある。
タイムアウトと再送回数は bring-up 時の値で、binding の既定より緩めてある。
新しいボードに載せるときはここを写すのが早い。

[app/boards/nucleo_g474re.overlay](../../app/boards/nucleo_g474re.overlay) は各プロパティを選んだ理由をコメントで説明してあるが、ピン割り当ては未検証のプレースホルダである（ファイル内にもそう書いてある）。
配線の根拠には使えない。

## 配線の要件

UART がトランシーバを**ハードウェアで**駆動できなければならない。
STM32 の UART なら `de-enable` プロパティがそれに当たる。
ドライバイネーブルをソフトウェアでトグルすると折り返し区間の前後にレイテンシが乗り、2 Mbps では成立しない。

`de-deassert-time` は小さく保つ。
この値はビット時間の 1/16 を単位とし、大きな値を与えるとこちら側のストップビットが終わってもトランシーバが有効なままになる。
その区間はエンコーダが応答を返し始める区間と重なるので、両方のフレームが壊れる。

トランシーバの受信側が常時有効になっているボードでは、送信したコマンドバイトが受信線に返ってくる。
バスノードに `tx-echo` を書けばドライバがそれを捨てる。
プロパティを書かなかった場合は、最初のトランザクションからドライバが判定する。

## 応答が落ちる理由と、ドライバ側の対処

2 Mbps では、コマンドバイトの送出から約 3 us でエンコーダが応答を始める。
ソフトウェアで受信を張るには短すぎるため、ドライバは init で一度受信を有効にし、通常運用中は止めない。
トランザクションごとに受信を張り直す実装は、あらゆる応答の先頭バイトを落とす最も確実な方法になる。

同じ理由から、ドライバは `UART_RX_BUF_REQUEST` に必ず応答する。
次のバッファを渡さないと受信がそこで永久に停止する。

エンコーダは連続するコマンドの間に間隔を必要とし、`inter-command-delay-us` がそれを与える。
これを置かずにコマンドを詰めて送るのが、応答が落ちるもう 1 つの典型的な原因である。

失敗したトランザクションは `max-retries` 回まで再送する。
エンコーダをオフラインと判定するのは、失敗が `offline-threshold` 回連続したときだけである。
それまでは最後に成功した値を保持し、stale として報告する。
応答が 1 回落ちただけで制御ループが乱れることはない。

応答が途中で切れた場合や長すぎた場合は受信を再同期し、UART が停止を報告した場合は受信を再開する。
1 回のスキャンが `poll-interval-us` を超過したときは、次のスキャンをキューに積まずに飛ばす。
特定のエンコーダの失敗が他のエンコーダの読み出しを遅らせることはない。

## 診断

3 段階に分かれており、製品ビルドではどのコストも負わない。

| 段階 | 有効化 | エンコーダ 1 台あたりのコスト |
| --- | --- | --- |
| `struct encoder_feedback.error_count` の集計値 | 常に利用可能 | 4 バイト |
| `amt21_get_stats()` と `amt21_bus_get_stats()` による原因別カウンタ | `CONFIG_ENCODER_AMT21_STATS` | 約 60 バイト、バス 1 本あたり追加で 24 バイト |
| `amt21_get_error_log()` による直近の失敗と受信した生バイト列 | `CONFIG_ENCODER_AMT21_ERROR_LOG_SIZE` | 1 エントリ 16 バイト |

カウンタは 32 bit で、ラップアラウンドする。
累計値として扱わず、2 回の読み出しの差を見る。

統計はエンコーダクラスの API ではなくドライバ固有の関数として公開している。
トランザクションが失敗する原因は RS485 プロトコルの性質であって、エンコーダ一般の性質ではない。

カウンタはエンコーダ単位とバス単位に分けてある。
UART のオーバーランはバス上の全トランザクションを乱すので、1 台のエンコーダに帰属させると誤解を招く。

## シェル

`CONFIG_ENCODER_AMT21_SHELL` を立てると `amt21` コマンドが増える。
実機での確認に使う。

```
amt21 list
amt21 read <dev>
amt21 stats <dev>
amt21 errlog <dev>
amt21 bus-stats <bus>
amt21 zero <dev>
amt21 reset <dev>
```

応答が落ちる原因を突き止めるには `amt21 errlog` が最短である。
実際に届いたバイト列が残るからである。

`app/debug.conf` は統計とエラーログの両方を有効にする。

## 注意点

- エンコーダ内部の更新レートより速くポーリングしても得られるものはない。
  そのレートは 14 bit 品で 100 us、12 bit 品で 25 us である。
- ノードアドレスは 4 の倍数でなければならない。
  下位 2 bit がコマンドを表す。
  1 本のバスに最大 64 台を載せられるのはこのためである。
- ゼロ点を保存できるのは単回転品だけで、多回転品に対する `encoder_set_zero()` は `-ENOTSUP` を返す。
  このコマンドと `encoder_reset()` はどちらもエンコーダを再起動させるため、約 200 ms のあいだ応答が止まる。
- 回転数カウンタは電源を切ると保持されない。

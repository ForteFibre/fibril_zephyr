# 0003. 複数用途のファームウェアを 1 つのアプリケーションと機能ライブラリで構成する

## Status

Proposed

## Context

このリポジトリは `app/` を 1 つだけ持ち、その中身は Zephyr の `example-application` の骨格にボード持ち込みの動作確認を足したものである。
実際に必要なファームウェアはこれ 1 つでは足りない。

扱う基板には 2 つの性格がある。
モータドライバや汎用センサ基板のように大会をまたいで使い回すものと、特定の対象に特化した RGB センサのように 1 つの大会でしか使わないものである。
そして 1 枚の基板が複数の機能を持つ。RC26 MainAir V01 は 6 系統の電磁弁出力と 2 系統の直交エンコーダ入力を同じ基板に載せている。

**基板と機能は 1 対 1 にならない。**
同じモータドライバ基板が、あるロボットではモータ 4 本を、別のロボットではモータ 2 本と電磁弁 4 個を担う。
逆に、違う基板が同じ機能の組み合わせを担うこともある。

node_id は実機ではディップスイッチか設定 ROM から起動時に読む。
だから機能の組み合わせと配線が同じ基板は、何枚あっても同じイメージで動く。

コードの重複は既に出ている。
`rgb_state.c` は 2 つのサンプルで完全に同一、`usbd_setup.c` は hub 系 2 つに重複し、`probe_logic.c` は 2 つの間で既に分岐している。
アプリを増やす前に置き場を決める必要がある。

fibril_can 側の事情も 2 つ効く。
生成される C シンボルの接頭辞はブロック型名だけで決まり、インスタンスは実行時引数である。
そして schema は複数ファイルに分割でき、参照されない型は blob に載らない（fibril_can の ADR-0015）。

## Decision

### 1. アプリケーションは役割ではなくバス上の立場で切る

`apps/node/` が fibril_can スレーブの唯一のアプリケーションである。
モータ用、電磁弁用のようにアプリを分けない。

`apps/` にはほかに、fibril_can を使わないボード持ち込みの動作確認と、トポロジの違うゲートウェイが並ぶ。

### 2. 機能はブロック型であり、型定義と実装を対で `lib/fibril_can_node/<type>/` に置く

`type.yaml` がバスから見た姿を、`impl.c` がその実装を持つ。
トピックを 1 本足せば両方を触るので、離すと片方だけ直す事故が起きる。

ハードウェアの扱いは `drivers/` に、fibril_can に依存しない制御ロジックは `lib/` の別の場所に置き、`impl.c` はその上に載る糊に保つ。

### 3. どの機能が生きるかは schema の `instances:` だけが決める

アプリケーションは、実装済みのブロック型の `type.yaml` を全部 codegen に渡す。
インスタンス化しない型は blob に載らず、生成マクロも出ない。
`impl.c` は本体を `#if defined(FCAN_<TYPE>_MAX_COUNT)` で囲み、型が無ければ空になる。

機能ごとの Kconfig を作らない。
schema と Kconfig の 2 つが同じ問いに答えると、食い違ったときにどちらが正しいか決められない。

### 4. インスタンスとハードウェアの対応は devicetree が持つ

機能ごとに binding を用意し、`gpios` のような phandle 配列の並びがバス上のインスタンス番号になる。
実際のインスタンス数はその長さから取り、schema の上限を超えていないことを `BUILD_ASSERT` で確かめる。

### 5. 焼く単位は snippet で表す

`snippets/<大会>/<名前>/` が、ノードの schema、Kconfig、devicetree overlay を 1 組で持つ。
1 つの snippet が 1 つのイメージである。

```shell
west build -b fibril_rc26_mainair_v01 apps/node -S rc26-air
```

### 6. トランスポートも devicetree で選び、実体は `lib/fcan_transport/` に置く

ノードは、CAN コントローラに直結していても hub の self port であってもスレーブ
である。違うのは HAL の出どころと `fcan_poll` を回すスレッドだけで、どちらも
ブロック型の実装が知るべきことではない。

アプリケーションが知るのは `init` / `hal` / `attach` / `run` の 4 つに限る。
`fibril,can-hub` のノードがあれば hub、無ければ `zephyr,canbus` の直結が選ばれる。

外部 port を USB に向けるかどうかも同じ軸に乗る。`gs_usb` のノードがあれば
CANnectivity の class を重ねる。ホストが列挙できるのは attach の後でなければ
ならないので、この順序はバックエンドの中に閉じ込める。

### 7. node_id は実行時に読む

同じイメージを複数の基板に焼けることが前提なので、node_id をイメージに焼き込まない。
schema のノード名に `{i}` を書くと起動時の node_id で置換される。

ディップスイッチや設定 ROM を読む `lib/node_id/` を用意するまでの当面は Kconfig の整数で与える。

## Consequences

機能を 1 つ足す作業が `lib/fibril_can_node/<type>/` を 1 つ作ることに閉じる。
同じ機能が、直結の基板でも hub を兼ねる基板でも、同じ機械語のまま動く。
アプリケーションはブロック型の名前を 1 つも知らない。機能は登録セクションに自分を載せ、`main` はそれを走査して `fcan_config_t::instance_counts` を埋める。

`instance_counts` は `FCAN_ARRAY_<TYPE>` を添字にして埋める。
ブロック配列の並びは schema から導かれるので、位置指定の初期化子はコンパイルが通ったまま別のブロックに数を渡す。

`lib/fibril_can_node/` の下は `schema_gen.h` に依存する。
これはアプリケーションのビルド生成物だが、Zephyr はアプリごとにツリー全体を再ビルドするので、`drivers/` が `devicetree_generated.h` に依存しているのと同じ関係である。
`fcan_invoke_codegen` が生成物のディレクトリを `zephyr_include_directories()` にも渡す必要があり、これは fibril_can 側の変更になる。

`apps/node/` 以外のアプリケーションは codegen を呼ばないので include パスが無い。
`CONFIG_FIBRIL_CAN_NODE` でこのライブラリを丸ごと落とす。

hub 構成では周期処理が `fcan_poll` と別のスレッドで走る。ドライバのループに
アプリケーション用のフックが無いためで、`tick` の契約は「単一のスレッドから
呼ばれる」までしか約束しない。publish 自体は commit が別コンテキストを前提に
作られているので安全側にある。

登録セクションの宣言はアプリケーション側に置く。
モジュールの CMakeLists から `zephyr_iterable_section()` を呼んでもリンカスクリプトに届かない。
LD テンプレート向けの `sections-ram.ld` と CMake リンカジェネレータ向けの `zephyr_iterable_section()` の両方が要る。

`west.yml` は fibril_can を revision で固定する。
ブロック配列の並びはワイヤの契約の一部であり、`main` を追いかけていると `instance_counts` の割り当てが黙って変わる。

## 却下した選択肢

**`apps/<大会>/<役割>/` に切る。**
大会ごとの資産がまとまる利点はある。
しかし大会をまたいで使う基板のファームウェアを大会の数だけ複製することになり、直す先が毎年増える。

**hub を別のアプリケーションにする。**
トランスポートが違えば `main` の後半が丸ごと違うので、分ける理由はある。
しかし hub を兼ねる基板が機能も持つ（RC26 MainAir V01 はトランシーバ 2 本と
空圧出力 6 系統を同じ板に載せている）以上、そのアプリケーションは機能の走査と
`instance_counts` の組み立てを自前でもう一度持つことになる。

**`apps/<基板>/` に切る。**
1 枚の基板が複数の機能を持つので、同じ基板がロボットによって違う機能の部分集合を担う。
基板と機能の組み合わせが 1 対 1 にならない以上、基板は鍵にならない。

**機能を Kconfig で選ぶ。**
`drivers/` が `zephyr_library_sources_ifdef` で並べている流儀に揃う。
しかし schema が同じことを既に決めているので、2 つが食い違ったときに解決できない。
生成マクロで囲めば、正本は schema 1 つで済む。

**schema の糊も `lib/` ではなくアプリケーションに残す。**
`lib/` が fibril_can なしで使える状態を保てる。
しかし扱うファームウェアの大半が fibril_can スレーブなので、その再利用性は仮定の話である。
機能あたり 20〜50 行を分けるために継ぎ目を 1 つ増やす価値はない。

**`instances:` を devicetree から生成する。**
配線とインスタンス数の重複が消える。
しかし schema の `count:` は静的な上限にすぎず、実行時の `instance_counts` は別に残るので、消えるのは手書きの片方だけである。
代償として、バスに何を出すかを述べた唯一のリストが生成物になってレビューの diff から消え、ROS の名前空間を devicetree に書くことになる。
数の正本を devicetree に置く狙いは、C 側を devicetree から組み立てることで生成器なしに達成できる。

# 0004. RobStride の制御 API を汎用 motor クラスと機種固有ヘッダに分ける

## Status

Proposed

## Context

RobStride のアクチュエータをこのリポジトリのドライバとして載せる見込みが立っている。
ROS 2 側には `robstride_actuator_bridge_ros2` という参照実装があり、プロトコルの解釈はそちらで実機に対して確かめられている。
ここで決めるのは、その解釈を Zephyr のドライバクラスにどう載せるかである。

RobStride のバスは classic CAN 2.0B、29 bit 拡張 ID、データ長 8 byte、1 Mbps である。
ID の上位 5 bit が通信種別、下位 8 bit が宛先の CAN ID で、その間の 16 bit は種別ごとに意味が変わる。
モータは 5 つの動作モードを持つ。
位置（プロファイル）、位置（サイクリック同期）、速度、電流の 4 つに加えて、位置と速度と kp と kd とトルク前置補償を 1 フレームで同時に渡す**運動制御モード**がある。
モードの切り替えにはパラメータ書き込みフレームが要り、書き込みの前にモータを停止させる必要がある。
ゲインと上限のパラメータは、payload に IEEE754 の単精度浮動小数点数をそのまま載せる。

現在の `include/drivers/motor.h` はこの形に合わない。
`motor_set_output()` が受け取るのは `enum motor_output_mode` と `int16_t` の 1 値だけで、モードは電流、速度、電圧の 3 つである。
運動制御モードは 5 つの値を同時に必要とするので、この署名では表せない。

速度指令を `int16_t` に載せる方法も見つからない。
速度の上限は機種によって ±33 rad/s または ±50 rad/s である。
mrad/s を単位にすると ±50 rad/s は 50000 となり `int16_t` に入らない。
1/100 rad/s まで粗くすれば入るが、線路上の量子化は 16 bit を全域に割り当てているので約 0.0015 rad/s であり、ドライバが線路より粗い値しか受け取れなくなる。
上限を `int16_t` の全域に対応させるスケールなら分解能は保てるが、そのスケールは機種ごとに違う値になる。
`enum motor_output_mode` はクラスの共有語彙なので、機種で単位が変わる量をそこに載せるわけにはいかない。

feedback の側は、値の意味そのものが既存の実装と揃わない。
`struct motor_feedback` の数値フィールドは `int16_t` と `int32_t` で、**このクラスは単位の契約を持っていない**。
`position` の幅は ADR 0005 で `int64_t` に広げるが、単位の契約がない点は変わらない。
唯一の実装である `drivers/motor/robomaster.c` が入れているのは、8192 counts/rev のロータ角を積算した生値、モータが報告する生の速度、生の電流、そして ℃ 単位の温度である。
RobStride が報告するのは SI の物理量で、対応する生値は 16 bit の量子化コードしかない。
量子化コードは機種ごとの上限表と組にしなければ物理量に戻らないので、表を持たない読み手には復号できない。

電流に至っては、報告されている量が違う。
RobStride のフィードバックフレームが載せているのはトルクであり、参照実装が返している電流はトルクをトルク定数で割って係数を掛けた推定値である。

devicetree の側にも決めることがある。
`dts/bindings/motor/motor-controller.yaml` は `bus: dji,robomaster` を直に書いているため、別のバスの子ノードからは再利用できない。

## Decision

1. **`motor_driver_api` は実装する。** `enable`、`disable`、`get_feedback` の 3 つは、上位がモータの機種を知らずに呼べる。全モータの一斉停止と死活監視をクラス越しに書けることが、この 3 つを共有する理由である。

2. **`motor_feedback` に載せるのは、`drivers/motor/robomaster.c` と同じ意味で読める値に限る。** `online`、`stale`、`timestamp_ms` は単位を持たない。`temperature` は ℃ の整数とし、robomaster が入れている値と揃える。`position` は ADR 0005 が定める積算カウントとして載せる。`velocity`、`current`、`orientation` は `valid_mask` を立てない。立てなければ、読み手が単位を取り違えようがない。

   立てない理由はフィールドごとに違う。
   `velocity` は Context に書いたとおり、分解能か機種非依存性のどちらかを失う。
   `current` は、そもそもモータが報告しているのがトルクである。
   `orientation` は robomaster が生カウントを入れているので、ここに rad を入れると同じフィールドが実装ごとに別の単位を指す。

3. **積算するカウントは、線路上の 16 bit コードそのものとする。** 位置は ±4π を 65535 段に量子化して送られてくるので、8π rad あたり 65535 カウントになる。このスケールは全機種で共通で、線路の分解能をそのまま保つ。ADR 0005 の決定 4 のとおり devicetree には持たせず、`doc/drivers/robstride.md` に書く。

4. **`motor_set_output()` はどのモードでも `-ENOTSUP` を返す。** 電圧指令はプロトコルに存在しない。速度と電流については、決定 2 と同じ理由で、クラスの共有語彙に載せられる単位がない。

5. **指令とパラメータの読み書きは `include/drivers/motor/robstride.h` に置く。** 引数は `float` で、単位は rad、rad/s、A、Nm とする。運動制御は 5 引数を 1 つの構造体で渡す。SI の feedback も `robstride_get_feedback()` としてここに置き、測定値としてはトルクを返す。これで `include/drivers/encoder/amt21.h` の前例は診断から制御へ広がるが、公開する対象が機種に固有であるという点は変わらない。

6. **ドライバが持つ内部状態は `float` の 1 組だけとする。** `motor_feedback` はそこからの写像であり、同じ量を 2 通りに保持しない。

7. **位置は積算した連続値で返す。** 線路上の位置は ±4π で折り返すので、ドライバが折り返しを解く。積算の責務をドライバに置くのは ADR 0002 と同じ判断であり、`drivers/motor/robomaster.c` がロータ角に対して既にしていることでもある。

8. **devicetree は transport の親ノードとモータの子ノードの二段にする。** `drivers/motor/robomaster.c` と同じ形である。親が `cans` と `master-can-id` と `feedback-timeout-ms` を持ち、子が `reg`（モータの CAN ID）と `model` を持つ。`master-can-id` は ID の下位 8 bit に載るホスト側の識別子で、バス全体で 1 つなので親に置く。

9. **バスの binding は robomaster と共有しない。** `dts/bindings/motor/motor-controller.yaml` を一般化すると `bus:` の値が変わり、`dji,robomaster-motor` 側の `on-bus:` も合わせて直すことになる。RobStride のためだけに既存のドライバの binding へ手を入れる理由がないので、RobStride 用のバス binding を別に置く。

10. **compatible の vendor prefix は `robstride` とする。** `dts/bindings/vendor-prefixes.txt` に 1 行足す。`dji,robomaster` が DJI のプレフィックスを使っているのと揃える。親が `robstride,bus`、子が `robstride,motor` になる。

11. **モード別のゲインと上限は devicetree に置かない。** 運転中に変える値であり、`robstride.h` の API から設定する。devicetree に置くのは機種、CAN ID、減速比、回転方向、そのモータで超えてはならない上限のように、配線と機体が決まれば変わらない値に限る。

12. **機種ごとの定数表は、実機で確かめられた機種だけを持つ。** 参照実装が値を持っているのは RS00 と RS05 の 2 機種である。他の機種は `model` の enum に加えず、データシートで確かめてから足す。

## Consequences

ドライバは `float` を使う。
ゲインと上限のパラメータが IEEE754 を payload にそのまま載せるので、内部を固定小数で書いても最後に変換が要る。
対象に想定している STM32G4 は FPU を持つ Cortex-M4F なので、`CONFIG_FPU` を有効にすれば実行時の負担にはならない。
ztest が走る `native_sim` でも問題にならない。

汎用 motor クラス越しに RobStride を他のモータと差し替えられるのは、`enable`、`disable`、死活監視、積算位置までである。
速度とトルクまで差し替え可能にするには `motor.h` に単位の契約を入れる必要があり、それは motor クラスを見直す時点でまとめて扱う。
積算位置についてスケールがドライバごとに違うことは残るが、これは ADR 0002 の決定 11 が encoder について選んだ形と同じである。

温度は ℃ の整数に丸めて `motor_feedback` に入れるので、線路上の 0.1 ℃ 刻みは汎用クラス越しには見えない。
過熱の判定に細かさが要る用途は `robstride_get_feedback()` を使う。

`master-can-id` を親に置くので、1 つの CAN コントローラにぶら下がる RobStride は 1 つのホスト ID を共有する。
同じバスに複数のホストを見せる構成は表せないが、その必要は今のところない。

fibril_can と同じ CAN コントローラを共有できない。
RobStride は classic CAN の 1 Mbps、fibril_can は CAN FD であり、ビットレートもフレーム形式も両立しない。
RobStride を載せるボードは、モータ用と fibril_can 用に別の FDCAN コントローラを割り当てる必要がある。
`fibril_robomaster_miniv4` と `fibril_rc26_mainair_v01` はコントローラを 2 つ以上持つので、この条件を満たす。

フィードバックはコマンドへの返信として返る。
周期的に指令を送っていれば周期的に状態が返るので、`drivers/motor/robomaster.c` と同じく `k_timer` から `k_work` を起こして送信する形になる。
指令を保存するだけの API が制御ループから呼ばれても、CAN の送信で待たされない。

ROS 側への露出はこの決定の範囲外とする。
`lib/fibril_can_node/` にブロック型を足す話は、ドライバの形が固まってから別に決める。

## 却下した選択肢

**`motor.h` に位置モードを足し、単位をドライバごとに文書で決める。**
クラスが 1 つで済み、上位から機種を意識せずに位置指令を出せる。
しかし単位をドライバごとに決めるのは、共有語彙である `enum motor_output_mode` に「値の意味は実装に聞け」という但し書きを付けることになる。
速度について、分解能を保つスケールが機種で変わることは Context に書いたとおりで、文書で決めても機種をまたいで同じ数値が同じ物理量を指さない。

**電流指令だけは汎用 API に載せ、単位を mA とする。**
電流の上限は機種によって ±15.5 A または ±11 A であり、mA という 10 進の固定小数のままどちらも `int16_t` に収まる。
4 つのモードのうち、分解能を落とさずに機種によらない単位を選べるのは電流だけである。
しかし `drivers/motor/robomaster.c` の `motor_set_output()` が受けているのは生の指令値であって mA ではない。
同じ `MOTOR_OUTPUT_MODE_CURRENT` が実装ごとに別の単位を指す状態になり、決定 2 で feedback について避けたことを指令側で招く。

**RobStride を motor クラスと無関係な独立したドライバクラスにする。**
`int16_t` との折り合いをまったく気にせずに済む。
しかし `enable`、`disable`、`get_feedback` まで別の関数名になり、非常停止のときに上位がモータの種類ごとに分岐することになる。
共有できるものまで手放す理由がない。

**`motor_feedback` に 16 bit の量子化コードをそのまま入れる。**
`drivers/motor/robomaster.c` が生値を入れているのと形が揃う。
しかし RoboMaster の生値がロータ角と rpm という意味の定まった量であるのに対して、RobStride の量子化コードは機種ごとの上限表と組にしなければ物理量に戻らない。
表を持たない読み手にとっては、値が入っていることが誤解のもとになる。

**`velocity` と `orientation` に機種非依存の SI 固定小数を入れる。**
汎用クラス越しに数値が物理量として読めるようになる。
単回転位置については実際に成立し、±4π は機種によらないので 1/10000 rad なら `int32_t` に線路より細かく収まる。
しかしそれを `orientation` に入れると、robomaster が同じフィールドに入れている生カウントと単位が食い違う。
速度は 10 進の固定小数では載らない。
一部だけ成立する規則をクラスに持ち込むより、`valid_mask` を立てないほうが読み手に正確である。

**`master-can-id` をモータの子ノードごとに持たせる。**
記述がモータ単位で閉じて読みやすい。
しかし RX フィルタはコントローラ単位で張るものであり、子ごとに違う値を書けるようにすると、フィルタを何本張るかが子ノードの書き方で決まってしまう。
バス全体で 1 つだと binding で示すほうが、実装と一致する。

**モード別のゲインを devicetree に置く。**
機体ごとの調整をボード定義に集められる。
しかし調整は実機を動かしながら繰り返すもので、そのたびにビルドし直すことになる。
devicetree に置くと、実行時に変えた値と定義の値が食い違ったときに、どちらが効いているのかを追う手間も増える。

**参照実装が持たない機種の定数を、公開資料から推定して表に入れる。**
対応機種が増える。
しかし上限値は指令の飽和と feedback の復号の両方に効くので、誤った値は静かに間違った物理量を返し続ける。
実機で確かめるまで表に入れない。

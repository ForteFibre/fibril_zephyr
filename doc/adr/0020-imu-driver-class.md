# 0020. ジャイロを、SI 単位と連続した yaw のスナップショットを返す IMU クラスで見せる

## Status

Proposed

## Context

PCMainFW（Main 2024 V1 の Mbed ファームウェア）が担っていた自己位置推定の入力を、fibril_zephyr の基板に移す。
その 1 つが UART のジャイロ R6093U である。
R6093U は約 100 Hz でパケットを送り続け、yaw は ±180° で折り返す。
自己位置推定（fibril_localization の `basic_deadreckoning`）は、折り返さない yaw を前提にしている。
PCMainFW は、ドライバが ±π をまたいだ回数を数えて連続値にしていた。

Zephyr には sensor API があり、加速度と角速度には標準のチャネルがある。
しかし roll、pitch、yaw のチャネルは無く、値は `struct sensor_value`（整数部と 10^-6 の小数部）で渡す。
読み出しは `sensor_sample_fetch()` と `sensor_channel_get()` の 2 段で、鮮度や途絶えたことを表す決まりも無い。

このリポジトリのエンコーダとモータは、独自のクラス（`include/drivers/encoder.h`、`motor.h`）で、最新の値のスナップショットと `online`、`stale`、`timestamp_ms`、`error_count` を返す。
ブロック型の実装（`lib/fibril_can_node/`）は tick ごとにそれを読む。

## Decision

1. **IMU クラス `include/drivers/imu.h` を足す。** API は `imu_get_feedback()` と `imu_reset()` の 2 つで、エンコーダクラスと同じく、ブロックしないスナップショットを返す。戻り値の約束（`-ENODATA`、`-EAGAIN`、`-EIO`）もエンコーダクラスに揃える。

2. **値は SI 単位（m/s²、rad/s、rad）の float で、センサの軸のまま返す。** エンコーダクラスは counts のまま返し、換算を制御層に任せる（ADR 0002 の決定 11）。換算に減速比や車輪径といったアプリの値が要るからである。IMU の換算係数はデバイスだけで決まるので、ドライバが持つ。軸を機体に合わせるのは、取り付けを知る消費者に任せる。

3. **yaw の連続化はドライバが行い、やり直しを `yaw_epoch` で知らせる。** 折り返しを正しく追えるのは、全てのサンプルを順に見るドライバだけである（ADR 0002 で積算をエンコーダドライバに置いたのと同じ理由）。連続化は 0.01 deg の整数で行い、丸めの誤差を溜めない。

4. **R6093U のドライバは割り込み駆動の UART API で受ける。** 38400 bps では DMA を使う理由が無く、async API が要求する DMA のチャネルを確保せずに済む。

5. **受信が止まる不具合への備えを、最初から入れる。** 受信の割り込みのたびに UART のエラーをクリアし、何も届かない間は watchdog が受信を張り直す。2020 年に、別のドライバで受信が止まったことがあるためである（fibril の wiki の r6093u のページ）。

6. **起動時にリセットのコマンドを送り、yaw を 0 にする。** PCMainFW と同じ振る舞いにする。

## Consequences

ブロック型は、エンコーダと同じ形で IMU を読める。
WT901B（I2C）など、ほかの姿勢センサのドライバも同じクラスで足せる。

yaw の符号はデバイスのままなので、R6093U では機体と逆向きになる。
消費者が反転する（`basic_deadreckoning` は今も `-yaw` で使っている）。

`imu_reset()` の後は yaw が 0 に跳ぶ。
消費者は `yaw_epoch` を見て、積分の状態を捨てる。

数百 ms 途絶えた間に半回転以上回ると、連続化が 1 回転ずれる。
途絶えた後に連続化をやり直すと、そのたびに yaw が跳んで `yaw_epoch` が進む。
ずれる場面よりも、短い途絶えのたびに自己位置推定が向きを失う方が困るので、やり直さない。

## 却下した選択肢

**Zephyr の sensor API に載せる。**
上流の仕組みに乗れる。
しかし roll、pitch、yaw は独自のチャネル（`SENSOR_CHAN_PRIV_START` 以降）になり、鮮度と途絶えたことを表すにも独自の決まりが要る。
fetch と get の 2 段は、tick ごとに最新の値を読む使い方に合わない。
エンコーダとモータが独自のクラスである以上、ここだけ sensor API にする利点が小さい。

**yaw を折り返したまま返し、消費者が連続化する。**
ドライバは小さくなる。
しかし消費者は、全てのサンプルを取りこぼさずに見なければならない。
fibril_can の周期送信は最新の値を送るので、ROS 側では途中のサンプルが落ちうる。

**async UART API（DMA）で受ける。**
AMT21 のドライバと同じ形になる。
しかし DMA のチャネルを 1 つ確保することになり、この速度では割り込みの数も問題にならない。

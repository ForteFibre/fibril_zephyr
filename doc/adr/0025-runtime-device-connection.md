# 0025. 機器の接続を、ビルドではなく起動時の param で決める

## Status

Proposed

## Context

デプロイ snippet は、機体ごと、構成ごとに増え続けている（#30）。
ADR 0014 で、ハードウェアの記述は `dts/fibril/` の断片に移った。
それでも、デプロイ snippet の overlay には、どのモータにどのエンコーダを組むかと、バスの上のどのアドレスに何が繋がっているかが残っている。

- miniv4 の `md-qdec4`、`md-amt4`、`md-rotor8` は、同じ役割（MdMotor）の snippet である。違うのは `encoders` の並びと、AMT21 のアドレスと、モータの台数だけである。
- AMT21 と RobStride は、ADR 0014 の決定 3 により、繋いだものだけを devicetree に書く。そのため、アドレスや ID が 1 つ変わるだけで snippet が 1 つ増える。
- ODrive の軸の `reg`（node ID）も、devicetree に書いている。rc26 の `odrive` は、6 軸の node ID を並べた overlay である。
- MdMotor を使う機体では、モータとエンコーダの組み合わせだけで、1 機体あたり 3〜4 個の snippet になる。

組み換えのたびにファームウェアを焼き直すことにもなる。
CanMotorMbed#245 は、バーニアエンコーダと冗長エンコーダを足すために、`robomaster_miniv4_vernier` と `robomaster_miniv1_vernier` というビルドのターゲットを別に増やしている。
同じことを fibril_zephyr で snippet に写すと、エンコーダの合成の仕方ごとに snippet が増える。
エンコーダの合成は、ADR 0026 で扱う。

一方で、ROS から渡す param はすでにある。
MdMotor の `adc/port` は、ADC のどのポートを読むかを実行時に選んでいる（255 はモータ自身の番号）。
ブリッジは param を保存し、プロビジョニングで START の直前に PARAM_SET で渡す（fibril_can の SPEC §8.3）。
スレーブが再起動すると、ブリッジは同じ値を渡し直す。

## Decision

### 1. 基板に関わる値を 4 つに分ける

| 区分 | 何か | 例 | どこで決めるか |
|---|---|---|---|
| **ボードの割り当て** | MCU のピンとペリフェラルの対応 | FDCAN2 を RoboMaster のバスに使う、RS485 の UART、qdec の timer | ビルド時（board の DTS、`dts/fibril/` の断片） |
| **機器の接続** | 基板の外に何が、どこに、どのアドレスで繋がっているか | 機器の型番（AMT21 の分解能と多回転を含む）、繋いだポートやバス、ID やアドレス、モータとエンコーダの組、機器のバスのホスト側の速度 | 起動時に param で読み、運転中は変えない |
| **制御の値** | 運転の中で調整する値 | `encoder/gain`、`invert`、ゲイン、減速比のような機械の定数 | param（今と同じ） |
| **保守操作** | 機器の側に保存された設定を書き換える | RobStride の ID やボーレートの変更、ID とボーレートの走査 | service（param にしない） |

このうち「機器の接続」を、devicetree から param に移す。

「ボードの割り当て」との境目は、基板の内側か外側かである。
基板の内側はピンの配線で決まり、ハンダ付けをしない限り変わらない。
基板の外側は、ケーブルの差し替えや機器の交換で変わる。

ID とアドレスは、機器の側に保存された値を、ホストが読みに行くための期待値として持つ。
ホストから ID を書き換える機能は、決定 9 の保守操作として別に持つ。

### 2. 機器の性質は機器表に置き、制御のブロック型は機種と ID で参照する

機器の型番、アドレス、ホストのバスの速度のような、機器そのものの性質は、ノードに 1 つだけ置く機器表のブロック型の param に持つ。
MdMotor のような制御のブロック型は、使う機器を「機種（u8）と ID（u8）」の組で参照するだけにする。
MdMotor なら、`motor/kind`、`motor/id`、`encoder/kind`、`encoder/id` のような param になる。

機器表を分けるのは、1 つの機器を複数のブロックが使うことがあるからである。
ギヤで同期させた 2 台のモータが 1 つのエンコーダを読む場合がそれにあたる（RC25 の射出の yaw）。
エンコーダの型番を、そのエンコーダを使う MdMotor ごとに持たせると、2 つの値が食い違ったときにどちらが正しいかを決められない。

### 3. ID とアドレスは、基板の中の同じ機種の間で一意にする

参照は「機種と ID」なので、同じ基板の同じ機種で ID が重なると、どの機器を指しているかが決まらない。
複数のバスがあっても、同じ機種では ID を重ねない。

RoboMaster と RobStride のドライバは、すでにこの形になっている。
`cans` に並べたバスのどれにモータがいるかは、最初の応答で決まる。
ID はトランスポートの中で一意である。

その代わり、1 つの基板に繋げる同じ機種の台数は、バスの本数によらず、その機種の ID の空間で頭打ちになる。
ID の空間が狭い機種ほど、この制約が効く。
RoboMaster の ID は 1〜8 なので、バスを 2 本にしても 8 台までである。
今の RoboMaster のドライバも、全バスで共通の 8 枠しか持たないので、同じ制約がある。
これは、参照を「機種と ID」の 2 つに保つための代償として引き受ける。
上限を超える台数が要る構成が出てきたら、この決定を見直す（却下した選択肢の「参照にバスを含める」）。

### 4. 参照の既定値は「未接続」にする

機器の参照の既定値は、「未接続」を表す値（`0xFF`）にする。
param を渡さなければ、ブロックは何も駆動しない。

エンコーダが未接続の MdMotor は、DUTY の指令だけを受け付ける。
速度と位置の指令は、ループを閉じる測定が無いので断る。

### 5. 接続は起動時に一度だけ読み、運転中には当てない

接続の param は、起動した後に初めて START に入るときに読む。
RUNNING の間に変わった値は、次の再起動まで当てない。
ブリッジは値を保存しているので、再起動すれば新しい値が渡される。

運転中にエンコーダを付け替えると、位置の基準が黙って変わり、制御が暴走しうる。
接続は、機体を組み直すときにしか変えない値なので、運転中に当てられる必要もない。

START の時点で、接続の param はすべて揃っている。
ブリッジは、param を複数の PARAM_SET に分けて送るときも、すべてが OK で返ってから START を送る。
1 つでも断られるか、応答が無ければ、プロビジョニングを巻き戻し、START を送らない（fibril_can の `node_agent_bringup.cpp`）。
そのため、一部の param だけが当たった機器表で駆動を始めることは無い。

### 6. 検証は 3 段階で行う

1. **ROS の側**：機体のリポジトリの CI で、param のファイルを検査する。ID の重複、存在しない参照、上限の超過を見る。
2. **スレーブの側**：構造の誤り（機器表に無い機器を参照している、などの誤り）を見つけたら、その構成で駆動しない。
3. **実行時**：機器が応答しない、または値が壊れているときは、決定 7 のとおり縮退する。届いたフレームが、宣言した型番と合わないことも、ここで見つけられる場合がある。たとえば、ドライバは C610 が温度を返さないとしているので、`c620` と宣言したのに温度の byte が 0 のままなら、型番の誤りを疑える。この判別の前提は、DJI の文書でも実機でもまだ確かめていない。devicetree に型番を書く今の形では、この照合はできず、型番を誤ると電流の換算が黙ってずれる。

ブロック型の `type.yaml` の `min` と `max` は、値の範囲の検査にだけ使える。
fibril_can は、範囲を値を送るマスターが PARAM_SET の前に検査し、スレーブのランタイムは検査しないと決めた（fibril_can の ADR-0022）。
ブリッジ（fibril_can#98）と Web マスター（fibril_can#100）は、範囲外の値を送らずに断る。
起動 YAML の範囲外の値は、スレーブに渡さず、スキーマのデフォルトのままにする。
接続の参照なら、デフォルトは「未接続」（決定 4）なので、範囲外の ID は「繋がっていない」として扱われる。

ただし、範囲の検査では、構造の誤り（機器表に無い機器を参照している、などの誤り）は見つけられない。
検査を持たないマスター（生の PARAM_SET を組むツールなど）からの値も、範囲外のまま届く。
そのため、段階 2 の構造の検査はスレーブのアプリが行う。
PARAM_SET そのものを断れるかどうかは、fibril_can にアプリの検証の hook があるかどうかで決まる。
SPEC の `BAD_VALUE` は残っているが、スレーブのランタイムは返さず、アプリが検証する経路も無い。
hook を足すかどうかは、まだ決めていない（未決の項目）。

### 7. 異常は、同期した群の単位で縮退させる

1 つの機器の故障や接続の誤りで、基板のすべての出力を止めることはしない。
止めるのは、その機器に依存する群だけにする。
群とは、一緒に止めないと機構を壊しうるブロックの組である。
群は param で宣言させず、接続の参照から導く。

- 同じ機器（モータかエンコーダ）を参照するブロックは、同じ群に入る。この関係をたどって繋がるブロックは、すべて同じ群である。
- ADR 0026 の合成エンコーダを参照するブロックは、合成エンコーダの入力の機器も参照しているとみなす。
- ADR 0026 の合成モータは、メンバーを含めて 1 つの群である。
- どの機器も共有しないブロックは、それだけで 1 つの群である。

宣言させないのは、決定 2 と同じ理由である。
参照とは別に群を書かせると、2 つが食い違ったときにどちらを信じるかが決まらない。
その代わり、機器を共有せずに機械的に結合したブロック（ギヤで繋いだ 2 台のモータが、それぞれ自分のエンコーダを読む構成など）は、群として見つけられない。
そうした構成は、ADR 0026 の合成モータで組む。

構造の誤り（決定 6 の段階 2）を見つけたときも、駆動しないのは、誤りを含む群だけである。

安全側に倒すなら、すべてを止めるべきかもしれない。
しかし、ロボコンでは、一部の機構が壊れていても、残りで競技を続けたい場面が多い。

### 8. 上限はビルドで決める

接続を実行時に選べるのは、ビルドで用意した枠の中だけである。

- バスに繋ぐ機器（AMT21、RobStride、ODrive、RoboMaster）は、バスごとに台数の上限を Kconfig で持つ。上限は、そのバスの帯域で決める。
- ポートと 1 対 1 で繋ぐ機器（qdec、ADC）は、基板のポートの数が上限である。

接続を param で決めるブロック型（MdMotor、RobstrideMotor、ODriveMotor など）は、常に Kconfig の上限（`max_count`）の数のインスタンスを持ち、その数で ANNOUNCE する。
今は devicetree の並びの長さがインスタンスの数を決めているが、この ADR で並びが無くなるためである。
ポートの数で数が決まるブロック型（CanPortDiag など）は、今のままにする。

どのインスタンスを ROS に出すかは、マスターの設定で選ぶ。
選ばなかったインスタンスについて、マスターは topic と param を作らず、フレームも割り当てない。
そのインスタンスの param はスキーマの既定値（参照は未接続）のままなので、何も駆動しない。
選び方はブリッジと Web マスターの機能であり、fibril_can の側で決める（fibril_can#103）。

インスタンスの数そのものを param にすることはできない。
param_index はインスタンスの数から決まるので（fibril_can の SPEC §4.2）、マスターが PARAM_SET を送れるのは、数を載せた ANNOUNCE を受け取った後である。

### 9. 保守操作は service にし、param にしない

機器の側の ID やボーレートを書き換える操作は、param ではなく service にする。
param はブリッジが再起動のたびに渡し直すので、書き換えの操作を param にすると、再起動のたびに書き換えが走る。

- **ID とボーレートの変更**：バス全体に対して行う。1 台ずつ変えると、途中で、ホストとボーレートの合わない機器ができる。全台に変更を保存させ、電源を入れ直し、ホストの側の速度を切り替える順にする。
- **走査**：繋がっている機器の ID とボーレートを探す。RUNNING でない間だけ受け付ける。結果は報告するだけで、接続の param には自動で反映しない。

機種ごとの対応は次のとおりである。

| 機種 | ID の変更 | ボーレートの変更 | 備考 |
|---|---|---|---|
| RobStride | フレームで変えられる | フレームで変えられる | 今のドライバは、どちらのフレームも実装していない |
| ODrive | 確かめていない | 確かめていない | 未決の項目 |
| AMT21 | できない | できない | 書き換えには、機体の中では繋いでいないピンへ信号を送る必要がある |
| RoboMaster | ホストからは変えない | 対象外 | ID は ESC の側で設定する |

### 10. 機器のバスのホスト側の速度は、接続に含める

RobStride や ODrive のバスで、ホストが使うボーレートは、起動時に読む接続の param にする。
機器の動作が不安定なときにボーレートを下げて試すことは多い。
そのたびにファームウェアを焼き直さずに済ませたい。

fibril_can のバスの速度（`FIBRIL_FCAN_BITRATE`）は、ビルド時のままにする。
これを param で変えると、param を受け取る経路そのものが変わってしまう。

### 11. snippet に残すもの

デプロイ snippet には、次のものだけが残る。

- 役割と、載せるブロック型（ADR 0003 の決定 3 と ADR 0014 の決定 5）
- `fcan-ns`、インスタンスの数の上限、`max_frames` のような、バスの上の約束
- ボードの割り当て

モータとエンコーダの並び、機器のアドレス、機器の型番は、snippet から無くなる。
miniv4 の `md-qdec4`、`md-amt4`、`md-rotor8` は、1 つの MdMotor の snippet にまとまる見込みである。
役割が違う snippet（MdMotor と RobStride など）は、別のままになる。

## 機種ごとの扱い

| 機種 | 接続の param にするもの | devicetree に残すもの |
|---|---|---|
| RoboMaster | どの ID のモータを使うか、型番（`c620` か `c610`） | バス（`cans`）。ESC 8 台は今も ADR 0014 の決定 3 で常に定義している |
| RobStride | ID、型番、ホスト側のボーレート | バス（`cans`）、`master-can-id` |
| ODrive | node ID、ホスト側のボーレート | バス |
| AMT21 | アドレス、型番（分解能と多回転） | RS485 のバス |
| qdec、ADC | どのポートを使うか | ポート（timer、チャネル） |

RoboMaster の型番は、電流の換算を決める。
型番を間違えると、エラーにならずに電流の値がずれる。

## Consequences

- ROS の param のファイルを書き換えて再起動すれば、モータとエンコーダの組み換え、AMT21 のアドレスの変更、RobStride や ODrive の ID の変更が、焼き直さずに済む。
- 同じ役割のデプロイ snippet は、基板ごとに 1 つにまとまる。snippet が増えるのは、役割か基板が増えるときだけになる。
- ドライバは、devicetree の子ノードの代わりに、Kconfig の上限の数の枠を持ち、起動時に機器表から ID やアドレスを当てることになる。AMT21 のドライバの `node_addr`、`resolution`、`multiturn` のような const の config は、実行時の状態に移る。
- 接続の誤りが、ビルドのエラーではなく実行時の誤りとして現れるようになる。そのため、決定 6 の検証と、どの機器が見えていないかを示す診断が要る。
- Web マスター（fibril_can の `@fibril/can-core`）は、START の前に param を注入しない。そのため、Web マスターで動かすと、接続の param は既定の「未接続」のまま START に入り、決定 5 により運転中の変更も当たらない。`autoStart` を切って START の前に手で送れば回避できるかもしれないが、値は保存されず、再起動のたびにやり直すことになる。fibril_can の側で、保存と START の前の注入を足す必要がある（fibril_can#101）。
- エンコーダの向きを qdec の `invert-direction`（devicetree）で合わせている構成は、それも param に移す必要がある。`invert` は指令と feedback とエンコーダをまとめて反転するので、エンコーダだけの向きを直す param が別に要る。
- 決定 8 により、使わないインスタンスの分も RAM を確保する。2026-11-20 に `apps/node/sample.yaml` の 11 シナリオで測った。
  - fibril_can が `fcan_heap` から取る量は、最大で 5568 B（rc26 の main と odom で、RobstrideMotor 8、Solenoid 8）になる。heap は 16384 B で固定なので、リンクした RAM は増えない。1 インスタンスあたりでは、MdMotor 約 430 B、RobstrideMotor 約 510 B、ODriveMotor 約 330 B である。
  - ブロックの状態は、MdMotor が 1 インスタンスあたり 340 B で、4 台の snippet を 8 台にすると 1360 B 増える。どのシナリオでも、使う RAM は 128 KiB の 44 % 以下にとどまる。
  - ドライバの枠は、今の 1 台あたりの大きさで見積もると、AMT21 を 16 台で 2176 B、RobStride を 8 台で 4032 B、ODrive を 8 軸で 2176 B になる。
- 決定 8 で ROS に出すインスタンスを選ばずに全部を出すと、未接続のインスタンスの topic と param が ROS にあふれる。MdMotor だけで param が 200 個になる。また、rc26 の main と odom で全インスタンスのフィールドをフレームに載せると、フィールドは 211 個になり、copy entry の上限（128）を超える見込みである。
- 一度接続して動かしたインスタンスを、スレーブを再起動せずにマスターの設定から外すと、スレーブには接続が残ったまま、ROS からは見えなくなる。決定 5 により、接続は起動後の最初の START でしか読まないためである。指令が来なくなるので止まるが、外したときはスレーブを再起動する必要がある。
- param の数が増える。MdMotor は今 25 個、RobstrideMotor は 29 個で、fibril_can の型あたりの上限 32 個に近い。fibril_can の ADR-0023 で、この上限を外す。

### 置き換える決定

ADR の本文は書き換えず、この ADR が Accepted になったときに、次の決定に、この ADR で置き換えたことを書き足す。

- ADR 0004 の決定 8 と決定 11：ID と型番を devicetree の子ノードに置くこと。上限（`max-current-ma`）をどうするかは、未決の項目に残す。
- ADR 0014 の決定 2：`motors` と `encoders` の並びをデプロイ snippet に置くこと。並びがバスの上のインスタンス番号になる点は残る。
- ADR 0014 の決定 3 のうち、AMT21 と RobStride を「繋いだものだけ書く」とした部分。

## 却下した選択肢

### 組み合わせごとに snippet を足し続ける

今の形である。
ビルドの時点で誤りが分かる。
しかし、snippet の数が機体と構成の数だけ増え、組み換えのたびに焼き直しになる。

### 参照にバスを含める

参照を「機種、バス、ID」にすれば、同じ ID をバスごとに使えるので、台数の上限はバスの本数に比例して増える（決定 3）。
しかし、どのバスにいるかを param で決めることになり、「最初の応答でバスが決まる」という今のドライバの前提を崩す。
今は、ID の空間を超える台数を使う構成が無いので、採らない。

### インスタンスの数をビルドの設定で決める

snippet か Kconfig に、上限とは別にインスタンスの数を置く。
未接続のインスタンスは ROS に出ず、fibril_can の変更も要らない。
しかし、台数を増やすたびに焼き直すことになり、組み換えで焼き直さないというこの ADR の目的が、台数には及ばない。
また、数で表せるのは先頭から何個かだけなので、`motor0` と `motor3` だけを使う構成は組めない。
決定 8 の形で増える RAM は、測った範囲で基板の RAM に収まる（Consequences）。

### インスタンスの数をスレーブの不揮発メモリに置く

保守操作の service で数を書き込み、再起動して ANNOUNCE し直す。
焼き直しは要らない。
しかし、fibril_can の SPEC §8.3 は、永続化はマスターだけで行い、フレームワークは不揮発メモリに触れないと決めている。
数が基板の中にだけ残るので、基板を交換すると数が戻らない。

### ANNOUNCE の前に、マスターがインスタンスの数を渡す

fibril_can のプロトコルに、数を渡す段を足す。
しかし、heap で確保する構成では、`fcan_init` の後にアロケータを呼ばない（fibril_can の不変条件）。
数を受け取る時点では確保が終わっているので、結局 `max_count` の分を確保することになり、決定 8 の形より RAM は減らない。
また、数で表せるのは先頭から何個かだけである。
スレーブのアプリも、どのインスタンスを使うかは接続の param で判断するので、数を受け取っても使い道が無い。

### 接続を運転中にも変えられるようにする

決定 5 のとおり、運転中の付け替えは位置の基準を黙って変える。
運転中に変えたい場面も思い当たらない。

### ID の書き換えを param にする

決定 9 のとおり、ブリッジが再起動のたびに param を渡し直すので、書き換えが繰り返し走る。

### 接続の誤りを見つけたら、基板のすべての出力を止める

param のファイルの誤りに対しては、安全側の振る舞いである。
しかし、ロボコンでは、一部の故障で機体全体が止まるほうが困る（決定 7）。

### 機器の性質を、それを使うブロックごとに持つ

機器表のブロック型が要らなくなる。
しかし、1 つのエンコーダを 2 台のモータが共有すると、同じ機器の型番を 2 か所に書くことになり、食い違ったときにどちらを信じるかが決まらない（決定 2）。

## 未決の項目

- **アプリの検証の hook**：fibril_can の PARAM_SET に、アプリが値を検証して断れる hook を足すか。fibril_can の側の ADR で決める。hook が無い間も、スレーブは誤った構成を受け取ったうえで、その群を駆動せず、診断に出す（決定 6 の段階 2、決定 7）。断れないことで変わるのは、誤りに気づく場所が PARAM_SET の応答から診断に移ることであり、誤った構成で駆動しないことは hook が無くても保たれる。fibril_can の ADR-0022 は、範囲の検査をスレーブに置く案（ROM と生成コードが増え、ランタイムに型ごとの比較を持ち込む）を却下した。hook はランタイムがアプリの関数を呼ぶだけで、範囲の表も型ごとの比較も持たないので、この理由には当たらないかもしれない。足すなら、fibril_can の側で ADR が要る。
- **RoboMaster の `max-current-ma` と、MdMotor の `duty-full-scale-ma`**：devicetree に残すか、型番と組で param にするか。ADR 0006 の決定 3 は、モータ自身が守る上限を devicetree に置くとしている。
- **ODrive の ID とボーレートの変更**：CANSimple でホストから変えられるかを確かめていない。
- **機器表の形**：機種ごとの配列の param にするか、どの機種を 1 つの機器表に入れるか。実装の ADR で決める。決めるときの基準は次の 2 つである。
  - 機種（u8）の番号の割り当て：番号は一度割り当てたら変えず、使わなくなっても再利用しない。機体の param のファイルに番号が残るためである。
  - 機種を足したときの互換性：既存の機種の param の名前と意味を変えずに足せること。ブリッジは param を名前で保存するので、名前が変わると機体の param のファイルを書き換えることになる。
